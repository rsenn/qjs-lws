  Talking to a Claude Code session

  Your TODO.md already ruled out the internal per-session socket
  (/run/user/1000/cc-socks/<pid>.sock plus a key file), so these are the
  documented routes, checked against the local claude 2.1.318:

  1. Headless, no existing session. claude -p --input-format stream-json 
     --output-format stream-json --verbose reads JSON user messages on stdin and
     emits newline-delimited events. --resume <id> or --session-id <uuid> picks
     the conversation, --include-partial-messages streams chunks, and
     --replay-user-messages echoes input. This is the cleanest fit for
     ollama-repl: spawn it as a child process and keep a long-lived pipe. The
     docs say streaming input needs -p and --output-format stream-json, and I
     found no source for combining --resume with --input-format stream-json, so
     test that.
  2. Background sessions. This is new in your local version and not covered by
     the search results, only by claude --help. claude --bg starts a detached
     session and prints an id. claude agents lists them, claude logs <id> prints
     recent terminal output, claude attach <id> opens one in your terminal, and
     claude stop and respawn manage them. I haven't seen a way to send input
     without attaching.
  3. Remote Control. claude --remote-control or /remote-control connects a
     running local session to claude.ai/code or the phone app. It is meant for
     people, one remote session per instance, and the session ends when the
     process stops. It is not a programmatic API.
  4. Agent SDK. The SDK resumes a session by id and has a streaming-input
     client. I couldn't confirm that it can attach to a session still running in
     another process, so that remains open.
  5. tmux. The session json (~/.claude/sessions/<pid>.json) names the pane
     ("tmux":"0:@8.%8"). tmux send-keys and capture-pane work with the live TUI,
     but it is fragile.

  Recommendation: route 1 gives ollama-repl a "Claude" conversation in the
  multi-conversation design that behaves like any other provider (messages in,
  streamed events out). Route 2 is worth a small test if you want a live,
  detachable session instead of one resumed by id.

● Restarts no longer nest. The fix is committed and pushed as 99a9bba, and it's
  installed.

  How it works: os.exec can only fork, so there is no true in-place exec.
  Instead, the first process, which holds the terminal, runs each restarted
  harness in turn. A process that was started by a restart writes the next
  command to /tmp/ollama-repl-restart-<first pid>.json and exits with status 75.
  The first process reads that file and runs it. Ten restarts now cost two
  processes instead of eleven. The fallback to the previous version when an
  edited harness dies at startup still works.

  Safety: the child only trusts that file when its parent is the process that
  started it. A worker session the harness launches inherits the environment
  variables but has a different parent, so it won't exit with 75.

  Tested in tmux: three ollama-repl-ctl restart calls left exactly two
  processes, the first one and the live one. /exit ended the terminal command
  with status 0 and the temp file was gone.

  Your current session: it still holds its old chain (the 16 processes), because
  it started before this build. The chain unwinds when you exit that session.
  The next restart of auto will leave the old chain in place and add one more
  level. After you /exit it and start it fresh, restarts will stay flat.
